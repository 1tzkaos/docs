<Update label="2026-10-29" description="Added: X-Cache: stale on wallet routes">
**Added.** Some wallet routes now answer from a short-lived per-wallet copy and mark an older copy with the response header `X-Cache: stale`. A response without the header is fresh. Nothing in the body changed.

- **Routes:** `/v2/pnl/wallets/{wallet}/history`, `/chart` and `/performance`; `/wallets/{w}/chart`; `/stats/trader/{wallet}`, the `stats` block of `/swaps/trader/{wallet}`, and GraphQL `trader { stats }`. How old a stale body can be is on [Quotas & errors](/concepts/quotas-errors#stale-responses).
- **`/wallets/{w}/holdings/basic`:** now cached 15 seconds per wallet. It was uncached.
- **`/stats/trader` and `/swaps/trader`:** if a refresh fails you get the stored copy (no older than 10 minutes, marked stale) instead of an error. With none to fall back on, a computation that does not finish in time is a `503` with `Retry-After: 5`.

<Update label="2026-10-29" description="Now documented: reconciled and reconciliation_source on positions, risk, chart and the batch routes">
**Additive, documentation only.** These keys were already in the responses; they were not described. A client that ignores keys it does not know is unaffected.

- **`reconciled` and `reconciliation_source`** tell you whether a figure was checked against the wallet's on-chain holdings. They are now described on `GET /v2/pnl/wallets/{wallet}/positions` and `/risk` (`live`, `snapshot` or `unavailable`), on `GET /v2/pnl/wallets/{wallet}/chart` inside `summary` (`live` or `unavailable`), and on `POST /v2/pnl/wallets/{wallet}/positions/batch` (`live` or `unavailable`).
- **`POST /v2/pnl/positions/batch`, `POST /v2/pnl/tokens/{token}/positions/batch` and `POST /v2/pnl/wallets/batch`:** the response carries the pair at the top level, where `reconciled` is `true` only when every item was checked and `reconciliation_source` is `live`, or `partial` when at least one was not. On the two positions batches each position also carries its own pair (`live` or `unavailable`); the summaries of `POST /v2/pnl/wallets/batch` already did.
</Update>

<Update label="2026-10-29" description="Additive: wallet stats fields, wallet window and DEX filters, pnl_mode on empty token position">
**Additive.** A client that ignores keys it does not know is unaffected.

- **`GET /wallets/{w}/stats`:** now returns `window`, `win_count`, `win_rate`, `best_trade_pnl_sol`, `best_trade_mint`, `worst_trade_pnl_sol` and `worst_trade_mint`, as the response schema describes. `sell_count`, `winning_sells`, `best_trade_sol` and `worst_trade_sol` are still returned and are now documented.
- **`GET /v2/pnl/wallets/{wallet}/tokens/{token}`:** `pnl_mode` is returned when `position` is `null`, as it is when there is a position.
- **`window` and `dex` on the wallet routes:** `window` on `/wallets/{w}/pnl/basic` and `/wallets/{w}/stats` also accepts `24h` and `7d`. `dex` on `/wallets/{w}/pnl/basic`, `/stats`, `/trades` and `/holdings` takes a comma-separated list of integer IDs and/or names, as `/holdings/basic` already did; a name that is not a DEX is ignored. These worked before; they were not documented.
- **Now documented:** `total_volume_usd` on `/wallets/{w}/pnl/basic`; `from_token` and `to_token` on each trade; `truncated` and `cost_basis_available` on `/wallets/{w}/holdings`; the `{ wallet, truncated }` answer that `/wallets/{w}/pnl/basic`, `/trades` and `/holdings/basic` send for a wallet whose history is too large to compute; `reconciled`, `reconciliation_source` and `truncated` on the `/v2/pnl/wallets/{wallet}` summary.
</Update>

<Update label="2026-10-15" description="Changed: Developer rate limit allows short bursts">
**Changed.** The Developer and Pro limits are now a rate with a short burst allowed, not a strict count per second. Free (strict 10 per second) is unchanged.

- **Developer and Pro:** the rates are the same, 100 and 500 requests per second sustained. Developer never gets more than about 120 in any one second. Before, a key could send its whole second's budget in one go. A client that does that can now get 429s, even though it is under its rate over the second. Spread your requests across the second.
- **429:** a `RATE_LIMIT_EXCEEDED` response carries `Retry-After: 1` (seconds), on every tier, Free included.
- **`GET /credits`:** on Developer and Pro, `current_window_used` is how much of your allowance is in use right now, on the same scale as `rps_cap` (0 when idle, `rps_cap` when used up). It is no longer a count of the requests in the last second. `current_window_remaining` is `rps_cap` minus that, and 0 means the next request would get a 429. `rps_window_secs` still reads 1. Free is unchanged.
</Update>

<Update label="2026-10-07" description="Breaking: GET /swaps/{signature} returns every swap of the transaction">
**Breaking.** `GET /swaps/{signature}` now answers with an envelope that holds every swap of the transaction, instead of one swap object.

```json
{ "signature": "2B9pP1c1…", "total": 2, "swaps": [ { "…": "swap object" }, { "…": "swap object" } ], "price_semantics": "…" }
```

- **Why:** a signature names a transaction, and a transaction can hold more than one swap (a multi-hop route, or swaps on several venues). In one measured hour (2026-10-07, 17:00 to 18:00 UTC) 6.0% of transactions did, and the largest held 13 swaps. The route used to answer with one of them, chosen arbitrarily, and hid the rest.
- **Migrate:** read the swap fields you used from each element of `swaps`. Each element is the swap object the route returned before, with the same fields. A transaction with one swap gives a one-element array, so a client that reads `swaps[0]` sees what it saw before for those.
- **Order:** `swaps` is in a fixed order (ascending `slot`, `block_tx_index` and `ix_index`, then `dex`), so the same request returns the same order. `total` is always `swaps.length`: the swaps of one transaction are not paged.
- **`price_semantics` moved.** It is now a field of the response body, as on the other `/swaps*` routes. The `x-price-semantics` response header is no longer sent.
- **Unchanged:** an unknown signature is still a 404, and a lookup that ran out of time is still a 503, never a 404.
- **Now documented on the swap object:** `ix_index` and `block_tx_index`. The API already returned them on every swap; they are the keys the order is built from.
</Update>

<Update label="2026-10-07" description="Additive: time-lock keys on the audit lock object">
**Additive.** The `lock` object of a token's audit (`GET /tokens/{mint}/audit`, and `audit` on `GET /tokens/{mint}`) can now say that the LP is locked for a limited time and until when. A client that ignores keys it does not know is unaffected.

- **New keys:** `kind` (`"time_lock"`), `unlock_at`, `status` (`"active"` or `"expired"`) and `time_locked_pct` (`{ value, status, as_of }`). They appear only when a time lock is known for the token's pool (today: UNCX concentrated-liquidity locks) and only on a `lock` that already exists. They never raise `secured_pct`.
- **How to read them:** `mechanism` and `secured_pct` still describe a *permanent* arrangement only. `mechanism: "unsecured"` beside `kind: "time_lock"` and `status: "active"` means nothing is permanent and the LP is locked until `unlock_at`. `status: "expired"` means the owner can withdraw at any moment. `time_locked_pct.value` is a share of that pool's position value at `as_of`, not of liquidity; the `lock` object's description under `GET /tokens/{mint}/audit` has the full reading.
- **Clarified:** `mechanism: "locked"` and `lp_burnt: true` mean a permanent lock (a burn, Raydium Burn&Earn, a Meteora DAMM v2 permanent lock). A time-limited lock (UNCX, Streamflow, Jupiter Lock) does not count as either. The previous description listed them under `locked`.
</Update>

<Update label="2026-09-29" description="Breaking: one error body">
**Breaking.** Endpoints that answered an error with `{ "success": false, "data": null, "error": "<string>" }` now answer with the documented envelope, where `error` is an object:

```json
{ "success": false, "error": { "code": "MISSING_PARAM", "message": "missing required parameter: pair_address" } }
```

- **Migrate:** branch on `error.code` ([the codes](/concepts/quotas-errors#error-codes)) instead of parsing the `error` string. The message text of a 4xx is unchanged.
- **Every error of these endpoints is now the envelope.** That includes the ones that had an empty body (a 400 over a batch cap, a 500, a wrong method) or a plain-text body (a query parameter that does not parse, or a `/graphql` request body that is not valid JSON). A path outside the API's routes can still be a 404 with an empty body.
- **New codes:** a missing query parameter is `MISSING_PARAM`, and a wrong HTTP method is a 405 `METHOD_NOT_ALLOWED`.
- **A 5xx message is now generic.** It no longer carries the internal cause; retry on `UNAVAILABLE`, `GATEWAY_TIMEOUT` or `INTERNAL`.
- **A malformed mint is a 400.** On `/tokens/{mint}/holders`, `/holders/top`, `/snipers`, `/insiders`, `/smart-money` and `/whales` it is a 400 `INVALID_PARAM` on every tier; before, it was an empty 200.
</Update>
